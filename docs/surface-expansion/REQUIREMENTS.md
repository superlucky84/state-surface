## 1. 문서 위치와 역할

이 문서는 페이지의 서버 데이터 준비, 레이아웃, 슬롯과 아일랜드를 하나의 자연스러운 트리로 작성하고, 기존 스트리밍 커널을 유지하면서 초기 JavaScript를 줄이는 확장의 요구사항이다. 2026-10-13 개정에서 선택형 클라이언트 라우터와 prefetch·지연 server 슬롯·타입 지정 액션·scoped CSS·prerender·콘텐츠 컬렉션·이미지 최적화를 1차 범위에 추가했다. 같은 날 개정에서 Express 의존을 걷어 낸 런타임 중립 서버 코어와 어댑터(Node 자체 서버·Express 호환·Bun·Deno·Cloudflare Workers)를 1차 범위에 추가했다. 외부 사용자가 없는 0.x 단계이므로 2.0 전체에서 하위 호환을 고려하지 않고 기존 API를 새 모델로 일괄 전환한다(AG-08). `docs/idea/`와 `NEXT_IDEA.md`의 방향을 계승하며, Astro의 단일 파일 작성 경험을 목표로 삼는다. Astro 전체 기능과의 동등성을 릴리스 기준으로 삼지는 않는다.

이번 작업 범위는 이 문서 개정과 `DESIGN.md` 작성까지다. 구현 계획·수동 검증 문서와 런타임 구현은 후속 범위이며, 전체 설계·계획이 완료됐다는 의미가 아니다. 1.x/2.0은 설계 세대를 뜻하며 현재 패키지 버전은 `0.1.0`이다.

## 2. 배경 및 문제 정의

현재 StateSurface는 "Server owns state, client owns DOM projection" 원칙과 NDJSON 상태 프레임을 사용한다. 실제 코드에서 확인한 개선 범위는 다음과 같다:

1. **불필요한 클라이언트 JavaScript 전송 (No Zero-JS)**:
   - `auto.ts`의 `eager: true` glob import로 인해 현재 방문한 페이지와 무관한 모든 라우트의 템플릿과 Lithent 런타임이 무조건 초기에 로드된다.
   - SSR 중심의 가이드나 소개 페이지도 해당 콘텐츠에 필요하지 않은 템플릿·플러그인 코드를 함께 로드한다.
2. **작성 경험의 분리 (DX Split-Brain)**:
   - 페이지 레이아웃은 raw HTML 문자열 결합(`joinSurface`, `stateSlots`), 라우트는 정적 객체 선언, UI 슬롯은 Lithent 컴포넌트로 나뉘어 개발자가 전체 화면을 직관적으로 조망하기 어렵다.
3. **하이드레이션 제어 부재**:
   - 컴포넌트를 브라우저 로딩 즉시(`load`), 화면에 보일 때(`visible`), 유휴 시간(`idle`) 등에 맞춰 지연 활성화하는 선언적 지시자가 없어 세밀한 성능 최적화가 어렵다.
4. **로컬 상태 수명의 계약 부족**:
   - `lithentBridge.ts`는 기존 마운트의 DataProxy props를 갱신한다. 보통의 갱신에서 인스턴스를 재생성하는 구조가 아니다. 이 기반을 활용하되 제거·교체·reset·지연 활성화의 상태 수명을 명시해야 한다.
5. **MPA 전환과 상태 복원의 범위 불명확**:
   - `client/styles.css`에 네이티브 MPA 크로스페이드가 이미 설정돼 있다. 헤더·내비게이션의 시각적 연속성과 페이지 간 로컬 상태 복원은 별도로 정의해야 한다.
6. **기존 기능과 신규 안전 계약의 구분 필요**:
   - `ui`/`uiChanged`, `surface.transition()`, `data-pending`과 액션 시작·종료 훅은 구현돼 있다. 현재 pending은 첫 프레임에서 해제된다. 컴포넌트 API, 완료 상태와 외부 입력 검증은 추가 작업이다.
7. **페이지 이동과 로딩 경험의 한계**:
   - 페이지 이동은 항상 문서 전체 로드다. `main.ts`는 문서당 한 번 초기화하며 History API·링크 가로채기·prefetch가 없다. 이동마다 공통 JS를 다시 평가하고 헤더·재생 중인 미디어·진행 중인 채팅 같은 상태가 사라진다.
   - 모든 페이지를 요청마다 SSR한다(`routeHandler.ts`). 바뀌지 않는 소개·가이드 페이지도 빌드 시 정적 출력이나 CDN 캐시 계약이 없다.
   - 느린 개인화 영역이 있으면 페이지 전체 응답이 늦어진다. boot transition으로 우회할 수 있지만 선언적 지연 슬롯과 fallback 계약은 없다.
   - 가이드 콘텐츠가 4천 줄이 넘는 `shared/content.ts` 객체에 있어 작성·검토·스키마 검증이 어렵다. 이미지 크기·포맷·지연 로딩을 다루는 도구와 컴포넌트 단위 CSS 범위 지정도 없다.
8. **서버 런타임의 Express·Node 고정**:
   - 서버 조립·SSR 응답·transition 스트림이 Express `req`/`res`에 직접 묶여 있다(`engine/server/index.ts`, `routeHandler.ts`, `hooks.ts`). 사용자 API도 Express `Request` 타입을 노출한다(`engine/shared/routeModule.ts`의 `params(req)`·`initial(req)`, `shared/i18n.ts`의 `req.headers.cookie`).
   - 실행 중 `node:fs`로 라우트를 스캔·동적 import하고(`routeScanner.ts`, `bootstrap.ts`, `assets.ts`), SSR 해시는 `node:crypto` 동기 API, 종료 처리는 `node:http` Server를 쓴다. 따라서 Bun·Deno·Edge 런타임에 배포하거나 Express 없이 자체 서버로 실행할 수 없다.
   - 핵심 로직(async generator transition, NDJSON 인코딩, protocol 검증, Lithent `renderToString`)은 런타임 중립적이므로 분리 비용이 작다. 테스트를 제외한 `engine/server/`는 약 1,100줄이다.

현재 구조는 확장에 적합하다. 주요 신규 작업은 `.tsx` 작성 모델과 빌드 플러그인, 빌드 의존성 분리, 서버 HTML 응답과 혼합 모드의 상태·생명주기 계약이다. 코드 근거와 검증 기록은 DESIGN.md에 정리한다.

## 3. 핵심 방향: 단일 파일 작성 경험 + StateSurface 스트리밍 커널

목표는 **서버 스크립트·마크업·레이아웃·아일랜드를 한 파일의 트리로 작성하는 경험**과 **Zero-JS 기본값·실시간 슬롯 스트리밍**을 함께 제공하는 것이다. 서버는 확정 데이터와 비즈니스 처리를, 클라이언트는 DOM 투영과 로컬 상호작용 상태를 소유한다. 단일 파일 목표는 사용자와 합의한 방향이며, 형식은 전용 확장자 없이 async 컴포넌트 `.tsx`로 정했다(DC-07).

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   StateSurface 2.0 Core Architecture                   │
├───────────────────────────────────┬────────────────────────────────────┤
│     Astro-Class DX & Islands      │    StateSurface Streaming Kernel   │
│ ───────────────────────────────── │ ────────────────────────────────── │
│ • Zero-JS by Default (정적 슬롯)   │ • 실시간 NDJSON 스트리밍 슬롯      │
│ • 선언적 지시자 (client:visible 등) │ • 세밀한 UI 패치 (class / cssVars) │
│ • 독립된 Lithent 아일랜드 수명     │ • Surface Capability 모델          │
│ • MPA View Transitions 전환       │ • AI Agent-Native 하네스 연결점    │
└───────────────────────────────────┴────────────────────────────────────┘
```

이동·로딩 경험은 Astro의 선택형 클라이언트 라우터(ClientRouter), `transition:persist`, prefetch, Server Islands, Actions, scoped CSS, prerender, Content Collections, 이미지 최적화를 참고한다. 클라이언트 라우터는 **서버가 렌더링한 다음 페이지 HTML을 받아 문서를 교체**하는 방식이다. 클라이언트 VDOM 라우터나 라우트 컴포넌트 트리를 브라우저에서 렌더링하는 SPA로 바꾸지 않는다.

## 4. 기능 요구사항 (Functional Requirements)

기존 R-01~R-14를 유지·보정하고 R-15~R-25를 추가한다. 각 요구사항의 검증 ID와 통과 기준은 DESIGN.md의 검증 매트릭스에서 정의한다. 렌더링 모드, 활성화 시점, 단건/스트리밍 응답, 콘텐츠 capability와 페이지 이동 방식(문서 로드/클라이언트 라우터)은 독립적인 선택 축이다.

### 4.1 렌더링 모드 및 아일랜드 아키텍처

- **R-01 (Zero-JS 기본 원칙)**:
  - 새로운 작성 모델에서 모드나 지시자가 없는 마크업·컴포넌트는 `static`으로 처리한다. static 전용 템플릿과 서버 전용 의존성은 클라이언트 빌드 산출물에서 제외한다. 다른 client 아일랜드가 실제로 사용하는 공유 모듈은 해당 경로로 포함될 수 있다.
  - static 콘텐츠는 방문 중 상태 프레임으로 교체하지 않는다. HTML 기본 상호작용은 허용한다. 슬롯 템플릿 JS 0바이트와 페이지 전체 실행 JS 0바이트를 구분한다. 기존 `defineTemplate()` 템플릿도 새 컴포넌트 정의로 전환하며 같은 기본값을 적용한다(AG-08).
- **R-02 (서버 전용 렌더링 슬롯 — `server` 모드)**:
  - 인페이지 갱신이 필요하지만 클라이언트 컴포넌트 로직은 불필요한 영역(예: 언어 전환, 서버 필터링 목록)의 경우, 서버의 등록된 템플릿에서 렌더링한 HTML 조각을 전송받아 슬롯 DOM만 교체한다. 클라이언트에 컴포넌트 JS를 내려보내지 않는다.
  - HTML 적용은 선언된 슬롯 내부로 제한하고 client 아일랜드와 DOM 소유권을 겹치지 않는다. 서버 상태 병합의 기준과 요청 간 수명을 명시한다.
- **R-03 (인터랙티브 Lithent 아일랜드 — `client` 모드)**:
  - 복잡한 상호작용이 필요한 영역은 독립된 Lithent 컴포넌트로 활성화하고 로컬 상태·이벤트·ref·생명주기를 지원한다. 기본적으로 SSR을 제공하며 활성화 후 Lithent가 내부 DOM을 관리한다. 독립 생명주기는 CSS·보안 샌드박스를 뜻하지 않는다.
- **R-04 (선언적 아일랜드 지시자 — Client Directives)**:
  - 개발자는 슬롯이나 컴포넌트에 간단한 속성을 선언하여 브라우저 활성화 시점을 통제할 수 있어야 한다:
    - `client:load`: 페이지 로드 즉시 컴포넌트 청크 로드 및 마운트.
    - `client:idle`: 브라우저 메인 스레드가 유휴 상태(`requestIdleCallback`)일 때 마운트.
    - `client:visible`: 슬롯이 뷰포트에 진입할 때(`IntersectionObserver`) 동적 로드 및 마운트.
    - `client:media="(query)"`: 지정한 미디어 쿼리가 일치할 때 마운트.
    - `client:only`: 서버 SSR을 생략하고 브라우저에서만 마운트.
  - `client:only`는 SSR 생략 정책이다. 활성화 시점과의 조합·기본값을 별도로 정의한다.
  - 지시자 충돌, 브라우저 API 미지원, 실패·재시도와 제거된 슬롯의 로드 완료를 처리한다. 지연 활성화 중 프레임과 첫 사용자 액션을 유실하지 않고 자동 boot transition은 클릭 없이 동작해야 한다.

### 4.2 빌드 파이프라인 및 자동 코드 분할 (Code Splitting)

- **R-05 (온디맨드 템플릿 청크 분할)**:
  - `eager: true` 기반의 전역 glob import를 폐기하고, Vite 플러그인 또는 빌드 매니페스트를 통해 **실제 각 라우트/슬롯에서 요구하는 아일랜드만 동적으로 분할 로드(`import()`)**하는 매핑을 자동 생성해야 한다.
  - client 컴포넌트와 CSS를 함께 로드하고, 서버 전용 코드가 client 모듈의 전이 의존성에 들어가면 빌드에서 진단한다. static/server 모듈을 lazy glob으로 산출물에 남기는 것만으로 R-01을 충족했다고 보지 않는다.
- **R-06 (경량 클라이언트 엔트리 분기)**:
  - 활성화할 인터랙티브 아일랜드가 없는 페이지는 무거운 Lithent 런타임을 배제하고, 최소한의 이벤트 위임(`data-action`) 디스패처만 로드하거나 JS를 완전히 배제할 수 있어야 한다.
  - 액션·boot·클라이언트 보강 기능이 없는 순수 static 페이지는 실행 JS를 삽입하지 않는다. server 액션 페이지는 액션·전송·HTML 적용 코드가 필요하다. Prism·목차·채팅 스크롤·디버그 기능은 필요한 페이지와 슬롯에서 선택한다.

### 4.3 스트리밍 프로토콜 및 UI 디자인 패치 확장

- **R-07 (단건 응답 및 스트리밍 응답의 독립 선택)**:
  - NDJSON 스트리밍 외에 일반 단건 `application/json` 응답 모드를 공식 지원하고, 동일한 프레임 파이프라인을 통해 슬롯에 적용할 수 있어야 한다.
  - Content-Type에 따라 명시적으로 읽고 완료·오류 의미와 async 함수/기존 generator 작성 계약을 정한다. 서버 HTML과 client props 모두 두 전송 방식을 사용할 수 있어야 한다.
- **R-08 (스트림 규약 강제 및 클라이언트 가드레일)**:
  - 성공 스트림의 첫 state 프레임은 full baseline이어야 하며 full의 대상 슬롯 집합을 정의한다. 구 wire와의 호환은 두지 않는다. 개발자가 쓰는 작성 프레임과 서버가 브라우저로 보내는 전송 op(`patch` + 슬롯별 `html`·`props`·`merge`·`remove`·`ui`, `reset`=full)를 분리하며, 전송 스트림은 `done`으로 끝나야 한다(DC-09).
  - baseline 이전의 오류 응답은 허용한다. `done`·치명적 오류·취소 뒤 추가 전송·적용을 차단한다. 서버의 기존 done 종료 처리도 유지한다.
  - 서버와 클라이언트에서 구조·슬롯 권한·capability·스트림 순서를 검증한다. 무효 프레임 드롭 뒤 partial/accumulate 적용을 이어갈 수 있는지 복구 정책을 명시한다.
- **R-09 (UI 디자인 패치 프로토콜 — `ui + uiChanged`)**:
  - 비즈니스 데이터(`states`)와 외형 스타일(`ui`)을 분리하여 `classAdd`, `classRemove`, `cssVars` 형태의 안전한 외형 변경을 데이터 재렌더링 없이 독립적으로 패치할 수 있어야 한다.
  - 기존 구현을 재사용하고 UI-only 프레임이 컴포넌트 갱신을 호출하지 않는지 검증한다. 입력 타입·클래스 토큰·CSS custom property를 검사하고 SSR 속성을 안전하게 직렬화한다. `ui=null`, full 교체, removed 우선과 SSR/클라이언트 일치를 검증한다.
- **R-10 (Surface Capability 모델)**:
  - 슬롯별로 허용 수준(`strict` 스키마 데이터 | `rich` 마크다운/블록 AST | `unsafe` raw HTML)을 정의하여 AI 에이전트나 동적 패치 시 안전성을 보장해야 한다.
  - 기본은 strict이며 프레임이 등록된 capability를 승격할 수 없다. rich의 허용 요소·URL·HTML 처리와 정화 정책을 정의한다. unsafe는 명시적 opt-in으로 제한하고 스크립트 실행·격리의 지원 범위를 정한다. 서버 템플릿에서 생성한 HTML도 외부 데이터를 검증해야 한다.

### 4.4 개발자 경험(DX) 및 상태 공존성

- **R-11 (페이지·레이아웃의 단일 파일 작성 모델)**:
  - 최종 작성 모델은 서버 스크립트와 템플릿을 한 파일에 두고 레이아웃·일반 마크업·server 슬롯·Lithent 아일랜드를 한 트리로 배치한다. 형식은 async 컴포넌트 `.tsx`다: 함수 본문이 요청마다 실행되는 서버 스크립트, 반환 JSX가 템플릿이며 페이지 옵션은 named export다(DC-07). 전용 확장자와 전용 컴파일러는 두지 않아 기존 TypeScript·포매터·린터·에디터 도구를 그대로 사용한다.
  - 재사용 컴포넌트는 별도 파일에서 import할 수 있고 문자열 결합을 기본 작성 방식으로 요구하지 않는다. `<Slot>`과 컴포넌트 지시자의 API 범위를 정의한다.
  - 요청 데이터는 요청마다 실행·격리하고 브라우저에는 허용된 props만 직렬화한다. 레이아웃 재사용·조건·반복·슬롯 식별 규칙을 제공한다.
  - `<Slot>`·client 지시자의 JSX 타입 선언을 제공하고, namespaced 지시자(`client:visible`)가 타입 검사와 빌드 변환을 통과해야 한다.
- **R-12 (서버 Props 스트리밍과 로컬 UI 상태의 공존)**:
  - 같은 슬롯 식별자·컴포넌트·reset 식별자가 유지되는 props 갱신은 기존 인스턴스를 재사용한다. 입력 초안·토글과 유지된 입력 DOM의 포커스를 서버 props 갱신 때문에 초기화하지 않는다.
  - 제거·컴포넌트 교체·명시적 reset·DOM 구조 변경의 상태 수명을 구분한다. 지연 활성화에서 SSR 기준 props와 최신 props의 차이를 처리한다.
- **R-13 (선언적 서버 액션 & Pending UI)**:
  - `data-action` 외에도 컴포넌트 내부에서 간편하게 서버 transition을 호출할 수 있는 런타임 API를 제공하고, 요청 처리 중 로딩/스피너를 쉽게 표시할 수 있는 pending 프리미티브를 지원해야 한다.
  - pending·성공·오류·취소 상태를 관찰하고 첫 결과 표시와 요청 전체 완료를 구분한다. 기존 pending 대상 지정 기능과 abort-previous 정책을 새 API에서도 제공하며 이전 요청 종료가 새 pending을 해제하지 않는다. 첫 이벤트의 폼 값·중복 실행·timeout·청크 실패를 처리한다.
- **R-14 (MPA View Transitions 통합)**:
  - 기존 네이티브 MPA 전환을 활용하고 크로스페이드·슬라이드 범위, 미지원 브라우저와 reduced motion의 fallback을 정한다. `document.startViewTransition()`의 인페이지 전환과 구분한다.
  - 헤더·내비게이션의 시각적 연속성과 상태 복원은 별도 계약이다. 문서 로드 이동에서는 필요한 값만 명시적으로 저장·복원하며 페이지 간 컴포넌트 인스턴스 보존을 보장하지 않는다. 클라이언트 라우터 이동에서는 R-17의 동일 문서 전환을 사용하고, 인스턴스 보존은 R-18로 명시한 요소만 대상으로 한다.

- **R-15 (슬롯 식별과 DOM 소유권)**:
  - 슬롯 인스턴스와 재사용 컴포넌트 식별자를 분리한다. 페이지 내 중복 식별자·URL 충돌을 진단하고 허용된 슬롯만 갱신한다.
  - 중첩 지원 범위와 부모 교체 시 cleanup·보존 정책을 명시한다. 런타임 메타데이터와 에이전트에 공개할 안전한 메타데이터를 구분한다.
- **R-16 (작성·빌드 진단과 scaffold)**:
  - 잘못된 지시자·서버 전용 import 유출·직렬화 불가능한 props·지원하지 않는 선언을 원본 파일 위치와 함께 진단한다. 소스맵과 편집기·타입 검사 지원 수준을 명시한다.
  - dev·production SSR·청크·CSS·생성 프로젝트가 같은 선언을 해석해야 한다. BASE_PATH, Tailwind 소스 탐색, scaffold 원본·overrides와 배포 버전 불일치를 검증한다.

### 4.5 페이지 이동·로딩·콘텐츠 경험 (Astro 참고, 1차 범위)

R-17~R-25는 2026-10-13 사용자 합의(AG-06)로 1차 범위에 포함한다. 모두 opt-in이며 선언하지 않은 페이지는 기존 동작을 유지한다.

- **R-17 (선택형 클라이언트 라우터 — 서버 HTML 교체 이동)**:
  - 레이아웃이나 페이지에서 opt-in하면 같은 origin·BASE_PATH 안의 링크 클릭과 GET 폼 제출을 가로채 다음 페이지의 SSR HTML을 fetch하고 엔진이 소유한 영역(SSR이 자동 삽입한 body·head 주석 마커 사이)만 교체·병합한다. 래퍼 요소를 추가하지 않으며 서드파티 스크립트가 동적으로 추가한 노드는 보존한다(DC-13). History API로 URL·뒤로/앞으로를 관리하며 View Transition API로 이동 애니메이션을 적용한다.
  - 교체 전 진행 중인 transition 스트림을 abort하고 사라지는 슬롯의 Lithent 인스턴스·플러그인을 cleanup한다. 교체 후 앵커 탐색·bootstrap·hydration·boot transition을 다시 실행한다. `data-action` 위임 리스너는 중복 등록하지 않는다.
  - `<head>`의 title·meta·stylesheet·청크 preload를 병합하고 중복 로드를 피한다. 새 문서의 `<script>` 실행 정책을 정의한다.
  - 이동 라이프사이클 이벤트(이동 준비 전, 로드 후, 교체 전, 교체 후, 페이지 준비 완료)를 제공하고 이동 취소와 URL·방향 정보를 노출한다. 문서 로드와 클라이언트 이동 모두에서 같은 "페이지 준비 완료" 이벤트를 발생시킨다.
  - 링크 단위 opt-out(가칭 `data-surface-reload`), 다른 origin·다운로드·`target`·수정 키 클릭·해시 이동은 브라우저 기본 동작을 따른다. 미지원 브라우저, JS 실패, 응답 오류, 다른 build ID의 응답은 문서 전체 로드로 fallback한다.
  - 스크롤 위치 저장·복원, 해시 앵커 이동, 새 페이지 제목 announce와 포커스 이동을 제공한다. reduced motion에서는 애니메이션을 생략한다.
- **R-18 (페이지 간 요소·아일랜드 유지 — persist)**:
  - 명시적 지시자(가칭 `transition:persist`, 식별자 지정 가능)를 단 요소·client 아일랜드는 다음 페이지에 같은 식별자가 있을 때 DOM·Lithent 인스턴스·로컬 상태를 유지한 채 이동한다. 재생 중인 미디어와 iframe도 대상이다.
  - 유지된 아일랜드에 새 페이지의 props를 반영하는 것이 기본이며 기존 props 유지(가칭 `transition:persist-props`)를 선택할 수 있다. 다음 페이지에 대응 요소가 없으면 정상 cleanup한다.
  - persist는 client 아일랜드와 static 요소만 대상으로 한다. server 슬롯·스트리밍 중인 슬롯의 persist 의미와 진행 중인 액션의 처리 정책을 정한다. 문서 전체 로드로 fallback되면 유지되지 않는다.
- **R-19 (Prefetch)**:
  - 링크·전역 설정으로 prefetch 전략(`hover`, `tap`, `viewport`, `load`)을 선언할 수 있어야 한다. 클라이언트 라우터가 있으면 받은 HTML을 이동에 재사용하고, 없으면 브라우저 prefetch 또는 Speculation Rules를 사용한다.
  - 다음 페이지에 필요한 아일랜드 청크·CSS를 함께 미리 가져올 수 있다. Save-Data·느린 네트워크에서는 자동 prefetch를 줄이고, 캐시 수명·중복 요청·인증 응답의 재사용 범위를 정한다. GET 이외 요청과 부작용이 있는 URL은 prefetch하지 않는다.
- **R-20 (지연 server 슬롯 — Server Islands)**:
  - 슬롯에 지연 지시자(가칭 `server:defer`)를 선언하면 페이지 셸을 먼저 응답하고 해당 슬롯은 fallback을 표시한 뒤 별도 요청으로 서버 렌더 결과를 채운다. 느린 개인화 영역이 페이지 전체 응답을 막지 않아야 한다.
  - 지연 요청에는 서버가 서명·암호화한 props만 사용하고 요청 쿠키·권한을 다시 확인한다. prerender·CDN 캐시된 셸 안에서도 동작해야 한다. 실패 시 fallback 유지와 재시도 정책, 이후 transition 프레임과의 순서를 정한다.
- **R-21 (타입 지정 서버 액션과 progressive enhancement)**:
  - 서버 액션을 입력 스키마와 함께 정의하고 서버에서 검증한다. 검증 오류를 필드 단위로 반환하며 client 컴포넌트에서 타입이 지정된 호출 API를 사용할 수 있어야 한다(R-13의 확장).
  - 액션을 대상으로 하는 `<form>`은 JS가 없거나 로드 전이어도 일반 POST로 동작하고, 서버는 결과를 반영한 페이지를 응답한다(POST-redirect-GET 포함). JS가 있으면 같은 액션을 transition으로 실행한다. 기존 transition generator와 상태 프레임 결과를 함께 지원한다.
- **R-22 (컴포넌트 범위 CSS — scoped CSS)**:
  - 컴포넌트 범위 CSS는 CSS Modules(`*.module.css`)로 제공한다. 해당 컴포넌트가 사용한 클래스에만 적용되고 전역 적용은 `:global()`로 명시한다(DC-07). 같은 파일 안 스타일 작성 방식은 후속 선택지다(DC-23).
  - 범위 지정 CSS는 SSR·server HTML 교체·client 렌더 결과에 같은 범위 표식을 적용하고, 청크·클라이언트 이동 시 필요한 CSS만 로드한다. Tailwind와의 공존 규칙을 정한다.
- **R-23 (Prerender와 하이브리드 출력)**:
  - 페이지별로 빌드 시 정적 HTML 생성(prerender)과 요청 시 SSR을 선택할 수 있어야 한다. 동적 라우트는 생성할 경로 목록을 제공한다.
  - prerender 페이지에서도 server 슬롯 transition·지연 server 슬롯·client 아일랜드가 동작한다. 요청별 데이터(쿠키 기반 언어 등)를 사용하는 페이지의 prerender를 진단하고, 언어별 경로 생성 등 i18n 처리 방침을 정한다. 정적 파일 서빙·BASE_PATH·캐시 헤더를 정의한다.
- **R-24 (콘텐츠 컬렉션)**:
  - Markdown(및 선택적으로 MDX 대체 형식)·JSON·YAML 콘텐츠를 디렉터리 단위 컬렉션으로 선언하고 frontmatter·데이터를 스키마로 검증해 타입이 지정된 조회 API를 제공한다.
  - 빌드·dev에서 스키마 위반을 원본 위치와 함께 진단하고, 콘텐츠 변경 시 dev에서 반영한다. 다국어 콘텐츠의 짝(parity) 검사를 지원하며 기존 가이드 블록 타입과 렌더러로 매핑할 수 있다. Markdown 렌더 결과는 R-10의 capability 정책을 따른다.
- **R-25 (이미지 최적화)**:
  - 이미지 컴포넌트는 width·height(또는 aspect-ratio)를 출력해 레이아웃 이동을 막고, 기본 `loading="lazy"`·`decoding="async"`, 반응형 `srcset`·`sizes`, 최신 포맷 변환을 제공한다.
  - 로컬 이미지는 빌드 시 변환하고, 원격 이미지는 허용 도메인 목록으로 제한한다. 첫 화면 이미지의 우선 로드를 선택할 수 있어야 한다.

### 4.6 런타임 중립 서버 코어와 어댑터 (1차 범위)

R-26은 2026-10-13 사용자 합의(AG-07)로 1차 범위에 포함한다.

- **R-26 (웹 표준 서버 코어와 런타임 어댑터)**:
  - 서버 코어는 웹 표준 `Request`를 받아 `Response`를 반환하는 단일 핸들러로 제공한다. 페이지 SSR, transition 스트림, 지연 server 슬롯(R-20), 서버 액션(R-21), 정적·prerender 자산 조회를 이 핸들러가 처리하며 Express·`node:*` API에 의존하지 않는다.
  - 사용자 API(페이지 데이터 준비, transition params, 액션 handler)는 Express `req` 대신 웹 표준 기반 요청 컨텍스트(요청·URL·params·cookie·locals·abort signal)를 받는다. Express `req` 호환 shim은 두지 않고 기존 라우트·훅을 일괄 전환한다(DC-27, 사용자 없는 0.x 단계).
  - 1차 지원 어댑터: **Node 자체 서버**(`node:http`, 외부 서버 의존성 없음, CLI 실행), **Express 호환 미들웨어**(기존 앱에 장착), **Bun**, **Deno**, **Cloudflare Workers**. 어댑터는 요청·응답 변환, 정적 파일 서빙, 종료 처리, 플랫폼 환경 변수 연결만 담당하고 동작 차이를 만들지 않는다.
  - production 실행은 실행 중 파일시스템 스캔 없이 빌드가 생성한 route·template·action·asset registry를 사용한다. dev 서버는 Node + Vite를 유지할 수 있다.
  - transition NDJSON은 `ReadableStream`으로 반환하고 취소는 `request.signal`로 감지한다. 보안 헤더·로깅·body 크기 한도·오류 페이지는 코어 옵션 또는 미들웨어 훅으로 모든 어댑터에서 같은 의미를 갖는다. BASE_PATH와 SSR 해시도 모든 런타임에서 같은 결과를 낸다.
  - 런타임별로 사용할 수 없는 기능(예: Edge의 빌드 외 이미지 변환, 파일시스템 기반 콘텐츠 로드)은 빌드 또는 시작 시점에 진단한다.

### 4.7 외부 SDK·태그 매니저 호환 (1차 범위)

- **R-27 (업체 기본 설치법 그대로 동작)**:
  - GTM·gtag, Sentry, Datadog RUM 같은 태그 매니저·관측 도구를 각 업체가 안내하는 기본 설치법(head 스니펫, CDN 로더, npm SDK `init`, 서버 SDK)대로 설치하면 문서 로드와 클라이언트 라우터 이동 모두에서 정상 동작해야 한다. 프레임워크 전용 우회 설정을 요구하지 않는다.
  - 앱이 모든 페이지에서 엔진보다 먼저 한 번 실행할 클라이언트 초기화 지점을 제공한다(SDK `init`용).
  - 엔진이 처리한 예상 밖 오류는 전역 오류 핸들러로 전달되어 관측 도구가 수집할 수 있어야 하며, 서버의 SSR·transition 오류도 서버 SDK에 연결할 훅을 제공한다.
  - 관측 도구가 감싼 `fetch`·`history`를 우회하지 않고, 트레이스 헤더(`sentry-trace`·`traceparent`·`baggage` 등)가 붙은 요청을 거부하지 않는다. production 소스맵을 업로드할 수 있어야 한다.

## 5. 비기능 요구사항 (Non-Functional Requirements)

- **NFR-01 (성능 및 번들 예산)**:
  - 대표 홈·가이드 페이지의 초기 실행 JS gzip 크기를 동일 기능의 기존 기준선 대비 70% 이상 줄인다. 액션 없는 순수 static 페이지의 실행 JS 0바이트는 별도로 확인한다.
  - 초기 JS에는 활성화 전 가져온 공통 코드·청크·플러그인·preload/prefetch를 포함한다. JSON·HTML·CSS는 별도 전송량으로 기록한다.
  - INP·CLS, 청크 로딩을 포함한 첫 액션 지연과 활성화 시 레이아웃 이동을 측정한다. 통과 수치·측정 환경은 DC-17에서 확정하며 FID는 신규 목표로 사용하지 않는다. 1~2kB 로더 목표의 압축 방식·포함 기능은 DC-04에서 정한다.
- **NFR-02 (일괄 전환과 기능 동등성 — 하위 호환 비고려)**:
  - 외부 사용자가 없는 0.x 단계이므로 하위 호환 레이어·legacy 경로·deprecation 기간을 두지 않는다(AG-08). 문자열 `layout(stateScript)` route, `defineTemplate` 기반 자동 hydration, Express `req` API, `TransitionHooks`, 구 wire 의미와 `__STATE__`/`__UI__`/`__BOOT__` bootstrap은 새 모델로 대체하고 제거한다.
  - 데모 사이트(`routes/`·`layouts/`·`shared/`), scaffold 원본·overrides, 공개 가이드와 `PROTOCOL.md`를 같은 변경 단계에서 새 API로 전환한다. 전환 후 기존 데모의 사용자 기능(언어 전환, boot, abort, 스트리밍, UI 패치, 액션, BASE_PATH, 플러그인)이 동등하게 동작해야 한다.
  - 배포 중 버전 불일치(이전 HTML의 새 서버 요청, 이전 청크 캐시)는 호환이 아니라 감지·reload로 처리한다.
- **NFR-03 (스타일 및 보안 격리)**:
  - UI 적용 대상은 해당 슬롯 엘리먼트이며 허용된 CSS custom property만 사용한다. 자식으로의 상속과 전역 CSS 선택자의 영향도 고려한다.
  - strict/rich에서 외부 상태·UI·콘텐츠가 스크립트나 이벤트 속성으로 실행되지 않도록 검증·이스케이프·정화하고 악성 입력 회귀 사례를 통과해야 한다.
  - 보호 대상은 외부 데이터와 프레임이다. 애플리케이션이 신뢰해서 설치한 악성 JS까지 일반 Lithent 마운트로 격리한다고 약속하지 않는다. unsafe의 추가 격리와 허용 정책은 TBD로 추적한다.
- **NFR-04 (이동 경험·접근성·견고성·서드파티 공존)**:
  - GTM·광고·위젯 등 서드파티가 런타임에 추가한 스크립트·iframe·노드는 클라이언트 이동 후에도 보존되고, 페이지뷰가 이동마다 집계되며, 엔진은 CSP `unsafe-inline` 없이 동작한다(V-30).
  - 클라이언트 라우터 이동은 같은 조건의 문서 전체 로드보다 체감 지연이 짧아야 하며 prefetch된 페이지는 네트워크 대기 없이 교체를 시작한다. 측정 지표와 통과 수치는 DC-17에서 정한다.
  - 반복 이동 후에도 리스너·Lithent 인스턴스·옵저버·플러그인 자원이 누적되지 않는다(메모리 누수 없음).
  - 이동 후 포커스·제목 announce·스크롤이 일관되며 키보드와 스크린리더 사용자가 새 페이지를 인지할 수 있다.
  - 라우터 런타임 크기는 NFR-01 초기 JS 예산에 포함하고, 라우터를 선언하지 않은 페이지에는 로드하지 않는다. JS 없이도 모든 링크·액션 폼이 문서 이동으로 동작한다.
- **NFR-05 (런타임 이식성)**:
  - 같은 앱 빌드가 1차 지원 어댑터 전부에서 같은 HTML·NDJSON 결과와 상태 코드를 낸다. 공통 적합성(conformance) 테스트를 모든 어댑터에서 실행한다.
  - 지원 런타임 매트릭스(최소 버전, 스트리밍·Web Crypto·파일시스템·이미지 변환 가능 여부, 요청 시간·CPU 한도)를 문서화하고 기능별 제약을 표시한다.
  - 서버 코어 번들에는 `node:*`·Express import가 없어야 한다. Edge 대상 번들 크기와 콜드 스타트를 측정해 기록한다. 통과 수치는 DC-17에서 정한다.

## 6. 제약사항 및 비목표 (Constraints & Non-Goals)

### 제약사항

1. 페이지 간의 기본 이동 모델은 **MPA(Multi-Page Architecture)**를 유지하며, 인페이지 변경은 명시적인 슬롯 경계를 통한다. 클라이언트 라우터(R-17)는 opt-in이며, 이때도 각 페이지의 HTML은 서버가 렌더링하고 라우팅·데이터 로드의 정본은 서버에 둔다.
2. 컴포넌트 라이브러리 인터랙션 엔진은 **Lithent**를 기반으로 경량성과 반응성을 극대화한다.
3. Vite 기반 번들링 파이프라인을 유지한다. 서버 코어는 웹 표준 `Request`/`Response`에 맞추고, Express는 1차 지원 어댑터 중 하나로 호환을 유지한다(R-26). dev 서버는 Node + Vite를 기준으로 한다.
4. 같은 DOM 내부를 서버 HTML 교체와 Lithent가 동시에 관리하지 않는다. 요청별 서버 데이터는 모듈 전역에 저장하거나 다른 요청과 공유하지 않는다.
5. AI 실행·추론·세션 운영은 후속 하네스의 책임이다. 이번 코어는 안전한 연결 계약을 준비한다.

### 비목표 (Non-Goals)

1. **React RSC / Flight 프로토콜 복제**: 복잡한 React Server Component 직렬화 프로토콜을 그대로 흉내 내지 않으며, StateSurface만의 단순하고 명확한 슬롯/프레임 프로토콜을 유지한다.
2. **범용 클로저 직렬화 (Universal Resumability)**: Qwik처럼 임의의 자바스크립트 클로저와 반응성 그래프 전체를 HTML에 직렬화하는 과도한 복잡성은 채택하지 않는다.
3. **전체 SPA 전환**: 라우팅 전체를 클라이언트 가상 돔 라우터로 대체하지 않으며, 브라우저에서 라우트 컴포넌트 트리를 렌더링하거나 클라이언트 전용 라우트 데이터 로더를 두지 않는다. MPA + View Transitions와 서버 HTML 교체 방식의 선택형 클라이언트 라우터(R-17)를 견지한다.
4. **전체 Astro 생태계 복제**: 모든 문법·통합(integration)·어댑터·배포 기능은 목표가 아니다. R-17~R-25로 선택한 개념만 StateSurface 계약으로 재설계한다. 페이지 간 DOM 인스턴스 보존은 R-18로 명시한 요소에 한정하며 암묵적 보존은 하지 않는다.

5. **비 JavaScript 서버 런타임 지원**: Python·Go 등 다른 언어 서버에서 페이지 SSR을 수행하는 것은 1차 범위가 아니다. NDJSON 프레임 프로토콜은 언어 중립적이므로 외부 백엔드가 transition 프레임을 생성하는 구성은 후속 범위로 검토한다.

6. **하위 호환 레이어**: 1.x 설계 세대 API의 shim·adapter·이행 경로와 구 wire 버전 지원은 목표가 아니다(AG-08).
7. **전용 페이지 파일 형식**: Astro식 `.surface` 확장자와 전용 컴파일러·언어 서버·문법·포매터 플러그인은 목표가 아니다. 페이지는 async 컴포넌트 `.tsx`로 작성한다(DC-07).

자동 동적 슬롯 생성과 서버 부모 안의 client 자식 보존은 최초 지원 범위를 정하기 전까지 지원한다고 가정하지 않는다. scoped CSS는 R-22로 1차 범위에 포함한다.
